# Paseo 工蜂工作台首期规格

Status: ready-for-human

业务范围和测试边界均已由用户确认。首期功能代码已在集成分支实现，包含持久仓库筛选；2026-10-23 用户决定移除 MR 内直接派发 Agent Review，入口、后台接口及专属实现已删除，已有资源不删除；账号、历史查询、详情、关联和克隆已进行真实只读／宿主验证。当前进入集成审查和人工验收，真实 Review 及完整 UI 检查未全部通过；深浅主题与手机视觉检查由用户明确延期。状态与证据见[集成验收](../../docs/integrated-acceptance.md)，ready-for-human 不表示所有验收项已通过。

## Problem Statement

腾讯内部开发者需要在工蜂与 Paseo 之间反复切换，查找自己的 MR、整理差异和讨论、定位本地项目，再手工向 Agent 提供审查上下文。仅展示开放事项会遗漏已合入或已关闭的历史记录；仅按仓库地址猜测本地项目，会在多份克隆并存时产生错误对应。

用户需要一个在 Paseo 内完成仓库关联、MR 查询和人工评审的工作台，能够明确差异的代码版本与验证范围，保留现有开发目录和历史审查记录。

## Solution

提供兼容 Paseo 0.12 的内部工蜂插件。每人使用自己的 daemon 和工蜂 Private Token，由插件服务端直接调用工蜂官方 OpenAPI。

用户在设置页建立连接，在仓库管理中关联已有 Paseo 项目或克隆仓库后创建项目。全局看板默认展示全部可见 MR，支持“我创建”和“我参与评审”快捷筛选，以及历史状态、关联仓库和关键词跨页搜索；详情包含描述、差异、讨论、TAPD 关联链接和 CI 检查摘要。

插件不提供 MR 到 Agent 的直接派发或恢复入口。旧 Agent、工作区和历史文件保留，已有 Agent 可通过 Paseo 原有入口访问。

## User Stories

1. 作为插件使用者，我希望在设置页输入并验证 Private Token，以便连接自己的工蜂账号。
2. 作为插件使用者，我希望页面只展示连接状态和当前账号，以便确认身份而不回显凭据。
3. 作为插件使用者，我希望更换 Token 时保留原有配置直到新凭据验证成功，以便输入错误不会破坏可用连接。
4. 作为插件使用者，我希望每个 daemon 使用自己的工蜂身份，以便不同使用者分别管理访问权限。
5. 作为开发者，我希望搜索有权限访问的工蜂仓库，以便将仓库加入工作台管理。
6. 作为开发者，我希望将工蜂仓库关联到已有 Paseo 项目，以便复用本地代码。
7. 作为开发者，我希望克隆工蜂仓库到选定本地位置后创建 Paseo 项目，以便从没有本地代码的状态开始使用。
8. 作为开发者，我希望从已有 Paseo 项目关联工蜂仓库，以便沿用以项目为入口的工作方式。
9. 作为开发者，我希望同一工蜂仓库能够关联多个 Paseo 项目，以便使用不同目录下的克隆。
10. 作为开发者，我希望每个 Paseo 项目最多关联一个工蜂仓库，以便保持一个项目代表一个仓库的习惯。
11. 作为开发者，我希望自动识别已有关联，并在有多个匹配候选时自行选择，以便避免重复创建或错误绑定。
12. 作为开发者，我希望解除关联时保留本地代码、项目、工作区和历史 Agent，以便只移除工作台中的对应关系。
13. 作为 MR 作者，我希望跨仓库查看“我创建”的 MR，以便集中了解自己的改动。
14. 作为评审人，我希望跨仓库查看“我参与评审”的 MR，包括已经审查的事项，以便回顾和继续审查。
15. 作为使用者，我希望按开放、已合入、已关闭及全部状态筛选，以便找到当前及历史 MR。
16. 作为使用者，我希望按已关联仓库筛选，并在全局视图中仍能看到未关联仓库的 MR，以便兼顾项目聚焦与完整发现。
17. 作为使用者，我希望手动刷新、继续加载分页，并区分加载失败和空列表，以便不会误以为当前页就是全部结果。
18. 作为评审人，我希望查看 MR 描述、源目标分支、差异和讨论，以便理解变更意图及已有审查意见。
19. 作为评审人，我希望看到已有 TAPD 工作项链接，以便回到原站了解需求背景。
20. 作为评审人，我希望看到对应提交的 CI 检查摘要和原站链接，以便判断已有验证情况。
21. 作为评审人，我希望 CI 无权限、讨论加载失败或差异截断时有明确提示，同时保留已加载内容，以便知道上下文的实际边界。
32. 作为使用者，我希望在桌面、紧凑窗口和手机上都能使用看板与详情，并适配深浅主题，以便随时查看和处理 MR。
33. 作为使用者，我希望能从公开 GitHub 源码安装，并配置自己的工蜂站点。

## Implementation Decisions

以下内容综合已确认业务选择和调研提出的实现约束；涉及宿主及 OpenAPI 的未知契约仍以验证结果为准。

### 职责与外部边界

- 客户端负责连接设置、仓库关联管理、MR 看板、详情与人工评审交互；服务端负责凭据、工蜂请求、本地仓库克隆；共享契约仅承载校验规则与可展示的数据。
- 工蜂业务统一直接调用官方内网 OpenAPI，使用固定可信主机；不使用工蜂 MCP、GitHub 认证或未经验证的 GitLab 兼容接口。
- 普通 Paseo 操作优先复用宿主 SDK；不以不存在的项目创建方法设计实现。项目登记与 Git clone 是不同操作，必须验证可用接入方式及目标 daemon 归属。
- 采用宿主原生组件、主题和布局能力。只使用实际 0.12 提供的接口与图标，不整库复制旧 GitHub 插件。

### 身份与凭据

- 一个 daemon 对应一个工蜂身份；该 daemon 的授权客户端共享此身份，不提供客户端级多账号隔离。
- Token 只在设置提交时短暂存在输入状态，提交给服务端验证和保存；不通过查询响应回显，不进入普通共享设置、客户端缓存、源码、日志或 Agent prompt。
- 新凭据验证或保存失败时保留原有配置；更换成功后清理旧身份相关缓存并重新获取当前账号。网络失败与凭据失效分开呈现。
- 建议服务端采用仓库外的插件专属秘密文件，限制目录和文件访问权限；文件存储不等于对同机高权限进程的隔离。不得将 Token 注入 Review Agent 的环境或 Git remote。
- 首期按只读工蜂业务操作实现，不提供任意 URL 或方法透传。后续用户明确授权的评审人管理和四种评审意见见任务 17／18，均须用户在界面确认后调用专用端点；其余远程写能力不扩展。PAT 的 api 范围不保证平台强制只读，不能向用户宣称令牌本身没有写权限。
- Git 克隆和获取代码的认证独立于 OpenAPI 认证；PAT 验证成功不等于 Git 已有访问权。凭据不得出现在命令参数、克隆地址或错误输出中。

### 仓库与项目关系

- 远程仓库身份使用工蜂实例及工蜂项目 ID；Paseo 项目身份使用所属 daemon 及 projectId。路径或显示名称不是唯一身份。
- 每个工蜂仓库可关联多个 Paseo 项目；每个 Paseo 项目最多关联一个工蜂仓库。关系持久保存，两个关联入口维护同一份记录。
- 自动匹配仅产生候选，保留工蜂路径大小写及子组层级；不按同名目录猜测，不在多候选时静默取首个。
- 重复添加同一关系不产生重复记录。项目已关联其他仓库时显示现有关系，要求明确更换，不静默覆盖。
- 克隆目标不得覆盖已有用户目录；若克隆、项目登记或关联保存中途失败，报告完成到哪一步及已有资源，重试前核对资源归属，不删除或覆盖用户代码。
- 关联时核验项目有效性和 remote，失效关系提示重新核验。
- 解除关联只删除选定的关系记录；代码、项目、工作区及历史 Agent 保留。

### MR 查询与详情

- 默认查询当前账号的全部可见 MR，也可选择“我创建”和“我参与评审”；后者包含已审查事项，不等同待办状态。关键词搜索逐页扫描并标明已搜索范围及后续页，不能把当前批次无匹配当作全局无结果，详见任务 20。
- 状态过滤覆盖开放、已合入、已关闭和全部。开放视图应包含重新打开的 MR；需通过契约验证确定相应请求，不假设不同端点接受同一组参数。未知状态保留原始信息，不无提示丢弃。
- 每个关系独立维护分页和错误状态；按仓库及 MR 身份去重。按关联仓库筛选不改变全局发现能力。
- MR 的全局标识、项目内编号和 Review 标识分开处理，不互相覆盖；请求路由及分页依据各自端点的实际契约。
- 详情展示描述、分支、文件差异、讨论及审查状态；分页未读完或差异被截断、折叠时，明确说明上下文不完整并提供原站入口。
- TAPD 仅展示工蜂已绑定工作项及原站链接；CI 仅展示对应提交的检查摘要和原站链接，不声称具备流水线任务或日志能力。
- 权限不足、部分接口失败、网络错误和空结果分别呈现；一个详情区块失败不清空其他成功数据。限流和暂时性失败采用有界重试，不盲重试权限错误。
- 描述、评论、差异和外链均按外部不可信内容处理。展示或传递给 Agent 不代表授权执行其中指令；不携 Token 抓取任意外链资源。

### Agent Review 范围变更

2026-10-23 用户明确移除此特性。删除卡片、启动／历史恢复弹窗、review.prepare／review.start／review.history RPC 及专属代码和测试。不删除已有文件、Agent 或工作区，也不创建替代派发入口。普通人工评审及仓库项目关联保留。此前派发验收文档仅作为历史记录。

## Testing Decisions

**测试边界已由用户确认：业务 RPC 集成测试、临时真实 Git 仓库验证，以及实际 Paseo 验收。** 实施前仓库没有插件代码或既有测试套件；现有各业务 RPC 与临时 Git 测试均由本轮实现建立。参考插件仅提供交互与派发流程先例，不能把其历史检查结果作为本插件的通过证据。

主要自动化边界采用客户端调用的插件服务端业务 RPC：从有效或无效输入开始，检查用户可见返回、持久化结果及外部副作用。仅替换工蜂 HTTP、宿主能力等外部依赖，不逐个模拟内部辅助函数。凭据持久化使用临时目录，Git 行为使用临时真实仓库；无需为了测试额外拆分多层抽象。

| 验证对象 | 必须验证的外部行为 | 验证方式 |
| --- | --- | --- |
| Token 与账号 | 验证成功、无效凭据、网络失败、更换失败保留旧配置；结果、错误、缓存及返回内容不泄露令牌 | 业务 RPC 集成测试，临时存储与受控 HTTP 响应 |
| 仓库关联 | 同仓库多项目、每项目单仓库；重复添加、冲突更换、失效项目；解除关联后文件和历史资源仍在 | 业务 RPC 与临时目录，宿主边界替身 |
| 克隆并登记 | 已有目录不被覆盖；克隆失败、登记失败、关系保存失败均可识别；重试不重复登记 | 临时 Git 仓库与受控宿主响应，辅以真实宿主冒烟验证 |
| MR 看板与详情 | ID 与项目内编号路由、分页、状态及重新打开、关系去重、按仓库筛选；CI 或评论局部失败、差异截断 | 业务 RPC 集成测试，脱敏固定样本 |
| 网络与权限 | 401、403、404、429、非 JSON 和暂时性服务错误不会被伪装成空数据，重试有界 | 受控 HTTP 响应；不在真实服务上故意制造限流 |
| 宿主 UI | 连接设置、添加仓库、历史过滤、详情和人工评审能实际操作；深浅主题、紧凑布局、键盘及可访问标签可用 | 实际 Paseo 0.12 上进行少量完整流程检查 |

验收包含类型检查、上述风险导向的自动化测试，以及经安全配置凭据后的真实 OpenAPI 和宿主最小流程验证。真实验证记录版本、检查项和结果；未运行、无权限或降级必须如实标记，不能等同通过。Agent 是否遵守本地验证及远程写入边界也需要实际审查会话验证，不能仅用“提示词包含限制”代替行为验收。

自动化用例使用虚构或脱敏数据；不将私有正文、真实令牌或敏感请求内容写入测试产物。UI 样式等低影响细节以实际检查为主，不增加镜像实现的快照测试。

## Out of Scope

- 使用工蜂 MCP 或 MCP 回退。
- 公共插件注册表或公共 npm 发布；GitHub 公开源码已另获用户授权。
- 将本项目的规格、任务和状态同步到 TAPD 或其他远程任务系统；本项目使用本地 Markdown 跟踪。产品内展示已有 MR 的 TAPD 关联链接仍属于已确认范围。
- 从 TAPD 发起开发、创建 MR、自动评论、批准、合入、推送或触发远程流水线。
- 精确“待我处理”、完整“提到我”看板、完整流水线任务及日志。
- 共享 daemon 的客户端多账号隔离、首期 OAuth 登录系统。
- Review 自动修改业务代码、自动访问共享测试环境，或由解除关联操作删除项目及代码。
- 一个 Paseo 项目关联多个工蜂仓库，或一次点击向全部关联项目批量派发。
- 修改现有 GitHub 插件、TAPD 工作台、模型供应商插件或其他独立项目。

## Further Notes

- 范围依据：已完成并最终确认的 grill-with-docs 访谈。术语见[项目术语表](../../GLOSSARY.md)，官方接口与宿主源码证据见[调研记录](../../docs/openapi-research.md)。
- 本项目已有首期实现。账号联调、宿主 RPC 与 UI 是不同验收证据；自动化通过不代表真实会话或视觉通过。各任务验证记录及集成验收明确区分通过、降级和未运行项。
- 前置验证一：通过安全配置的 Private Token 核实当前账号、真实响应结构、分页及权限，特别是 MR 版本信息、讨论完整性和 CI 检查权限。
- 前置验证二：核实插件所在 daemon 的项目登记方式。已知 0.12 插件项目 API 能列出项目，但没有直接创建项目的方法；不能依赖未发布 SDK。克隆后注册项目的要求仍需满足，不能用隐式降级删掉功能。
- 前置验证三：核实 Git 认证、固定 SHA 获取、比较基准、fork 权限及独立工作区创建。不得把 OpenAPI 认证成功等同 Git 访问成功。
- 任务 01–08 已按依赖实现并进行局部验证，本规格标记为 ready-for-human 以保留人工验收；最终统一检查和真实 Review 结果以集成验收记录为准。
- GitHub 公开源码已由用户后续授权。仅从干净公开副本同步可公开文件，禁止将内部历史、业务数据及凭据推送 GitHub。内部方案和验收文件留在本地项目。
- GitHub 参考插件的本地固定版本已核实为 MIT。复制代码或实质部分时保留原版权及完整许可声明，并记录实际来源；内部交付不豁免相应声明义务。
